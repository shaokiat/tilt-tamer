# Preflop Poker Trainer - Spec (45-minute showcase build)

Purpose: a small, verifiable project to try out the AdaL coding agent. Range logic and data reference: see `RANGES.md` (source of truth for assumptions, formulas and invariants).

## Stack

Single-page app, no backend for P0-P2. Vanilla JS or React + Vite (decide before starting). Unit tests for the logic (Vitest/Jest or equivalent).

## Priorities

### P0 - Core drill (must ship)
- `ranges.json` generated by a script implementing RANGES.md section 3 (script committed, output committed).
- Random (hand, position) deal. Positions: UTG, HJ, CO, BTN, SB.
- Buttons: Fold / Raise.
- Feedback: correct / perfect / wrong, action frequencies, and a 13x13 grid for that position's range with the dealt hand highlighted (pairs on the diagonal, suited above, offsuit below).
- Label in the UI: "Simplified ranges, not solver output".
- Scoring function pure and unit tested (RANGES.md section 4).

### P1 - Stats
- Accuracy overall, by position, and by category (pairs / suited / offsuit). Persist in localStorage.
- "Leaks" list: the 5 weakest (position, category) combos with at least 5 attempts.
- Reset button.

### P2 - Bring your own chart
- Load `ranges.custom.json` (same schema as RANGES.md section 5) in place of the generated data when present.
- Validate on load against the invariants that apply to custom data (schema, 169 hands, frequencies sum to 1). Do NOT enforce nesting or target % on custom data; show a warning instead.
- Show the active source ("rule-generated" or custom) in the UI.

### P3 - Coach chat (lower priority, only if time remains)
A side panel to ask questions and get explanations about the current hand and ranges.
- Context passed to the model: current hand, position, the range frequencies for that spot, the user's answer, and the text of RANGES.md.
- Must state that ranges are simplified approximations when relevant, and must not claim solver accuracy.
- Provider is pluggable behind one interface `ask(question, context) -> string`. Ship an offline stub that answers from templates (e.g. why a hand is in/out of range using its score and the cutoff), so the feature works without an API key.
- If a real LLM provider is added, the API key must NOT live in client code. Use a tiny local proxy or env-injected server route.
- Out of scope for P3: postflop advice, opponent modelling.

### Stretch (pick at most one, after P0-P2)
- Facing-an-open spots (BB/BTN defending).
- Hand-vs-range equity calculator (Monte Carlo), checked against known values (e.g. AA vs KK about 82/18).
- Spaced repetition: missed hands return more often.

## Acceptance criteria

- All invariants in RANGES.md section 6 pass as automated tests.
- Dealing 1000 random hands never produces a hand outside the 169 classes; frequency of pairs/suited/offsuit is roughly 6/1326 : 4/1326 : 12/1326 per class.
- Browser check: grid layout is correct (AKs above the diagonal, AKo below, AA on the diagonal); highlighted cell matches the dealt hand; stats update after each answer; reload keeps stats.
- No console errors.

## What to compare when trying the agent

- Quality of the initial plan and whether it asked about open decisions.
- Whether ranges stay in data (JSON), not hardcoded.
- Whether nesting and combo-count tests exist and pass on the first run.
- Bugs the browser agent found vs bugs you found.
- What the review pass caught.
